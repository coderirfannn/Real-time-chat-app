# ChatLock — End-to-End Encryption (E2EE) & Cryptography Architecture

This document details the Signal Protocol implementation in **ChatLock**, covering key generation, Extended Triple Diffie-Hellman (X3DH) session establishment, the Double Ratchet message protocol, ChaCha20-Poly1305 AEAD symmetric encryption, and zero-knowledge server relaying.

---

## 1. Zero-Trust Architectural Boundary

ChatLock enforces a **Zero-Knowledge / Zero-Trust** cryptographic architecture:
- **Client Ownership of Secrets**: Private keys (`identityKeyPair.privateKey`, `signedPreKey.privateKey`, `oneTimePreKeys[].privateKey`, `rootKey`, `chainKeys`, `messageKeys`) are generated and stored strictly on user devices.
- **Server as Untrusted Public Registry & Ciphertext Relay**: The server only stores public keys, signed pre-key signatures, and forwards encrypted payloads. The backend **never** possesses, derives, or inspects shared secrets or plaintext message content.

```
+---------------------------------------------------------------------------------------------------+
|                                       CLIENT A (ALICE)                                            |
|  - Generates Identity Key ($IK_A$), Signed Pre-Key ($SPK_A$), One-Time Pre-Keys ($OPK_A$)         |
|  - Hardware Keychain / IndexedDB Key Storage                                                      |
|  - Encrypts Plaintext -> Ciphertext + AAD via ChaCha20-Poly1305                                  |
+-------------------------------------------------+-------------------------------------------------+
                                                  |
                         Encrypted Ciphertext Payload (Zero Plaintext)
                                                  |
                                                  v
+---------------------------------------------------------------------------------------------------+
|                                 SERVER / REDIS / MONGODB RELAY                                    |
|  - Public Key Registry ($IK_{pub}$, $SPK_{pub}$, $OPK_{pub}$)                                     |
|  - Forwards `e2eePayload: { ciphertext, nonce, ratchetKey, pn, n }`                              |
|  - Generates Privacy Push: "🔒 New encrypted message"                                             |
|  - NEVER sees plaintext or private keys                                                           |
+-------------------------------------------------+-------------------------------------------------+
                                                  |
                         Encrypted Ciphertext Payload (Zero Plaintext)
                                                  |
                                                  v
+---------------------------------------------------------------------------------------------------+
|                                       CLIENT B (BOB)                                              |
|  - Retrieves Ciphertext + Header from Socket / REST API                                           |
|  - Derives Matching Message Key via Double Ratchet                                                |
|  - Decrypts and Authenticates Ciphertext via ChaCha20-Poly1305 + AAD                              |
|  - Caches Decrypted Plaintext in Memory / DecryptedCacheService                                   |
+---------------------------------------------------------------------------------------------------+
```

ChatLock utilizes audited pure TypeScript/JavaScript primitives from `@noble/*`:

| Functionality | Primitive / Standard | Implementation |
| :--- | :--- | :--- |
| **Digital Signatures** | Ed25519 (EdDSA) | `@noble/curves/ed25519` |

| **Random Number Gen** | Cryptographically Secure PRNG | `crypto.getRandomValues` / `crypto.randomBytes` |

## 3. Key Bundle Subsystem

Upon initial setup or login, each client device generates and registers a cryptographic key bundle:

1. **Identity Key ($IK$)**: Long-term Ed25519 keypair identifying the device.
2. **Signed Pre-Key ($SPK$)**: Medium-term X25519 keypair with an Ed25519 signature generated by $IK_{priv}$. Periodically rotated (default: every 7 days).
3. **One-Time Pre-Key (OPK) Pool**: Batch of 50 ephemeral X25519 keypairs. The server tracks consumed state and serves each OPK exactly once via atomic MongoDB operations.

```typescript
interface PublicDeviceKeyBundle {
  userId: string;
  deviceId: string;
  identityKey: string;           // Hex-encoded Ed25519 public key
  signedPreKey: {
    keyId: number;
    publicKey: string;           // Hex-encoded X25519 public key
    signature: string;           // Hex-encoded Ed25519 signature
    createdAt: string;
  };
  oneTimePreKey?: {
    keyId: number;
    publicKey: string;           // Hex-encoded X25519 public key
  };
}
```

## 4. X3DH Session Agreement Protocol

When Alice initiates communication with Bob for the first time:

1. **Fetch Pre-Key Bundle**: Alice requests Bob's public key bundle from `GET /api/v1/e2ee/keys/:userId`.
2. **Verify Signature**: Alice verifies Bob's $SPK$ signature using Bob's $IK_{pub}$.
3. **Generate Ephemeral Key ($EK_A$)**: Alice generates an ephemeral X25519 keypair.
4. **Montgomery Conversion**: Alice converts Ed25519 identity keys to Curve25519 format via `ed25519.utils.toMontgomery()`.
5. **Diffie-Hellman Key Agreement**:
   - $DH_1 = \text{ECDH}(IK_A, SPK_B)$
   - $DH_2 = \text{ECDH}(EK_A, IK_B)$
   - $DH_3 = \text{ECDH}(EK_A, SPK_B)$
   - $DH_4 = \text{ECDH}(EK_A, OPK_B)$ (If OPK was available; gracefully falls back to 3-DH if pool is empty).
6. **Master Shared Secret ($SK$)**:
   $$\text{SharedSecret} = \text{HKDF-SHA256}(DH_1 \parallel DH_2 \parallel DH_3 \parallel DH_4, \text{salt}=0^{32}, \text{info}=\text{"ChatLock-X3DH-v1"})$$
7. **Session Package**: Alice sends the first message containing an `initHeader` (`initiatorEphemeralKey`, `signedPreKeyId`, `oneTimePreKeyId`).
8. **Inbound Processing**: Bob parses the header, retrieves matching private keys, executes the identical 4-DH computation, and initializes the symmetric session.

## 5. Double Ratchet Protocol & Out-of-Order Decryption

Once the master secret is established, communication enters the continuous **Double Ratchet**:

```
                              [ Root Ratchet (DH) ]
                           /                         \
                          v                           v
              [ Sending Chain (HMAC) ]    [ Receiving Chain (HMAC) ]
                     |                                   |
              +------+------+                     +------+------+
              |             |                     |             |
              v             v                     v             v
          [ Message 1 ] [ Message 2 ]         [ Message 1 ] [ Message 2 ]
```

### 5.1 Symmetric Key Ratchet (Chain KDF)
For each message sent or received in a sequence:
- **Message Key**: $MK = \text{HMAC-SHA256}(CK, \text{0x01})$
- **Next Chain Key**: $CK_{next} = \text{HMAC-SHA256}(CK, \text{0x02})$
- **Forward Secrecy**: Once a message is encrypted or decrypted, $MK$ is immediately deleted. Past messages cannot be decrypted even if current keys are compromised.

### 5.2 Diffie-Hellman Ratchet (Root KDF)
When a reply is received containing a new public ratchet key:
- Generates a fresh DH output: $DH = \text{ECDH}(RatchetKey_{local}, RatchetKey_{remote})$
- Advances the Root Ratchet: $(RK_{next}, CK_{recv}) = \text{HKDF-SHA256}(RK, DH)$
- Generates a fresh local DH keypair and sends the public key in subsequent headers.
- **Break-in Recovery (Post-Compromise Security)**: Even if a session key is compromised at time $T$, future messages cannot be read once new DH ratchets complete.

### 5.3 Out-of-Order Message Handling & Replay Protection
- **Skipped Message Keys Table**: If a message arrives with a gap in the counter sequence ($n > n_{expected}$), intermediate message keys are computed, added to a bounded skipped keys table (`RatchetState.skippedKeys`), and associated with a 14-day TTL.
- **DoS Boundary**: Maximum skipped keys per sequence capped at `MAX_SKIP = 2000`; table capacity capped at `MAX_SKIPPED_KEYS = 1000`.
- **Anti-Replay**: Any replayed message whose counter is older than the chain or whose key has already been consumed is rejected immediately.

## 6. Secure Key Storage Strategy

| Platform | Storage Technology | Security Guarantees |
| :--- | :--- | :--- |
| **iOS** | Apple Keychain (`expo-secure-store`) | Hardware enclave encryption, persistent across app reinstalls. |
| **Android** | Android KeyStore (`expo-secure-store`) | Hardware-backed keystore, chunked storage respecting 2KB value limits. |
| **Web (Browser)** | Isolated `IndexedDB` (`chatlock_e2ee_keystore`) | Isolated from `localStorage`, cookies, Redux/Zustand state, and URL params. |
| **Testing / Node** | Secure In-Memory Store | Isolated volatile dictionary for Vitest automated test suites. |

## 7. Decrypted Message Caching (`DecryptedCacheService`)

Because Double Ratchet message keys are strictly single-use and destroyed after initial decryption:
1. Re-reading or re-rendering messages during scroll, screen focus, or upward cursor pagination would fail if relying on re-decryption.
2. The client implements `DecryptedCacheService`—an in-memory and encrypted persistent local cache.
3. Decrypted plaintexts are stored indexed by `serverMessageId` and `clientMessageId`.
4. Outbound messages authored by the local user are cached upon transmission, ensuring the sender never attempts to decrypt their own ratchet steps.
